## Mirra Band 独立版｜完整产品与技术方案

我建议把下一阶段命名为 Mirra Band Standalone V1。它不是推翻 Module 03/04，而是在已经验证的通信能力上增加一个独立的腕端学习引擎。

手环：独立学习引擎

本地书籍、第一步、计时、休息、已完成记录

结束后的可靠同步

去重上传 · 手机确认保存 · 更新书籍目录

手机：统一学习记录

阅读历史、页码进度、去重统计、备份

### 1. 数据所有权必须分清楚

| 数据              | 谁负责     |
| --------------- | ------- |
| 手环进行中的独立学习      | 手环      |
| 手环尚未同步的完成记录     | 手环      |
| 手机自身的学习 Session | 手机      |
| 已同步腕端记录的手机副本    | 手机      |
| 统一阅读历史和趋势统计     | 手机      |
| 主线及选定书籍的目录同步    | 手机为主要来源 |

进行中的手环 Session 不转换成手机活动 Session。 即使两端重新连接，手环继续管理自己的学习，直到主动结束并保存。

同时保留 Module 04 的在线控制能力，但必须明确区分「独立学习」和「控制手机学习」，不能让一次操作同时修改两套 Session。

### 2. 腕端本地数据模型

独立版最少需要三类持久化数据：

| 数据    | 关键字段                                   |
| ----- | -------------------------------------- |
| 书籍目录  | 书籍 ID、名称、主线标记、总页数、同步页码、默认第一步           |
| 当前学习  | 唯一 Session ID、已确认第一步、当前状态、开始时间、学习与休息区间 |
| 已完成记录 | 结束时间、可选结束页码、区间时长、同步状态、来源标记             |

学习和休息应保存为独立时间区间。例如：学习 20 分钟、休息 10 分钟、学习 15 分钟，最终学习时间为 35 分钟，而不是 45 分钟。

第一步动作确认属于每次 Session 的实际记录，不能因为完成过一次，就在下一次自动跳过。

本地数据写入失败时，应用不得显示虚假的“保存成功”。在存储无法可靠写入之前，也不能继续创建更多可能丢失的新学习记录。

### 3. 同步采用手机持久化确认

手环结束并保存

记录标记为“待同步”，保留在手环本地。

手机连接后接收

根据设备 ID 与 Session ID 去重，并验证记录合法性。

手机事务提交成功

先保存完整记录，再发送持久化确认。

手环收到确认

改为“已同步”。即使确认消息丢失，下次重传也不会重复导入。

同步成功后，不建议立即删除腕端原始记录。应保留一段可恢复的历史，并在空间不足时采用有明确保护条件的清理策略；未确认同步的记录永远不能为了清空间而自动丢弃。

### 4. 手机数据库需要正式扩展

现有 Mirra 的 Room v4 以手机业务 Session 为核心，还有唯一活动 Session、监测和结束保存约束。

因此腕端离线记录不应伪装成一个普通手机 Session。

建议新建有独立来源身份的完成记录及同步收据数据模型，再通过统一阅读历史的查询层融合。实现时可以规划 Room v5 迁移，同时必须将腕端导入记录纳入完整备份与恢复；旧备份格式应继续可读取，不允许因新增功能损害原有备份能力。

统计时仍保持原规则：跨设备的可信学习时间区间取并集；休息不计入阅读时间；未经监测的腕端阅读不冒充已验证有效专注。

# Mirra Band Standalone V1

## 独立学习与结束后同步 — 产品及实施合同

### 一、项目定位

Mirra Band 必须可以在手机关机、蓝牙断开或手机不在身边时，独立完成：

选择已保存书籍 → 确认第一步 → 开始阅读 → 休息 → 主动继续 → 结束 → 本地保存。

与手机重新建立可用通信后，自动上传已完成记录，手机确认持久化成功后，手环标记同步成功。

进行中的独立学习不向手机实时迁移所有权，也不自动转换为手机活动 Session。

原 Module 03 的只读同步、Module 04 的在线控制均保留，但与独立学习明确隔离。

### 二、已批准产品规则

1. 主线书籍自动同步，其他 IN_PROGRESS 书籍由手机端手动选择。
2. 手环离线使用最后一次可靠保存的书籍目录。
3. 每次开始新学习之前必须实际完成并明确确认第一步动作。
4. 没有手机提供的默认第一步时，可在手环选择具体预设动作；不能直接跳过。
5. 选择动作不等于完成动作。第一步确认前不得创建正式独立 Session。
6. 息屏、返回表盘或退出腕端应用不自动结束学习。
7. 休息 5/10 分钟结束后仍保持休息，用户点击继续学习才重新计入学习时间。
8. 允许在休息中直接结束整场学习。
9. 结束页码可选；未填写不推进书籍页码。
10. 手机和手环各自的原始记录都保留。
11. 同一设备的同一 Session 不得因多次同步重复导入。
12. 同书进度采用较高的合法页码，不因同步回退。
13. 双端重叠学习时间在全局统计中去重，按有效学习区间求并集。
14. 腕端独立学习标记为未监测，不能伪造手机有效专注或原有转化指标。
15. 双端历史统一展示，明确来源。

### 三、第一阶段：国行 9 Pro 本地存储可行性

**这是独立模式开发的真实技术前提。**

先查阅并核实小米 Vela 官方 system.storage、system.file、应用生命周期和目标设备 API。

在不破坏现有正式应用记录的前提下，使用隔离测试数据和可核对的实验版本，验证：

- 字符串、结构化记录的实际写入和读回；
- 返回表盘、息屏后重开，内容是否仍在；
- 应用被终止后重新启动，内容是否仍在；
- 同签名 RPK 安全升级后，本地记录是否保留；
- 写入失败、损坏、部分写入和中断场景的恢复；
- 设备重启后的保存情况与时钟可靠性；
- 可以支持的实际记录数量、单次写入延迟和空间限制。

不得把官方 API 文档存在等同于目标固件已验证。

选择能在目标设备可靠运行的持久化方式。优先考虑小型结构化记录、双槽版本化快照、序列号和校验值；具体提交方案须通过断点与损坏恢复测试，不能未经验证声称文件 move 或 storage.set 具有原子性。

每次开始、休息、继续和结束均先保存成功，再更新界面为确认状态。

若持久化或恢复不可用，停止进入真实用户数据开发，不以手机在线控制模式冒充独立模式成功。

### 四、第二阶段：腕端独立学习引擎

建立独立的 Local Session 状态机：

IDLE → PREPARING → FOCUS ↔ BREAK → FINISHED_PENDING_SYNC → SYNCED。

保持唯一正在进行的腕端 Session。

PREPARING 保存选中的书籍及第一步动作。只有用户主动确认第一步完成且记录成功后，才能进入 FOCUS。

FOCUS、BREAK 保存各自的开始和结束边界。BREAK 倒计时到零不自动改变业务状态。

退出应用后不依赖 JS 后台持续运行，而在重新进入时依据持久化时间锚点重建展示。

时间处理必须进行设备真机验证：

- 正常同一时间基准的退出与恢复可继续累计；
- 检查时钟倒退、异常跳跃、重启和持久化中断；
- 无法可靠判定的区间标记时间不确定，保留原始事实，不把猜测值计入可信时长；
- 如有适用且可验证的单调时间能力，优先使用并核对重启边界；
- 不伪造后台持续运行证据。

结束学习时可以不填写页码。记录存储失败则停留在可恢复状态，不宣称保存成功。

不得在手环中复制手机 Room、分心监测和有效专注算法。

### 五、第三阶段：离线书籍目录

手机决定主线与手环可用书籍集合。

腕端保存 phoneBookId、目录版本、书名、总页数、上次确认页码、默认第一步和主线标记。

主线自动加入，其余由手机界面选择。腕端列表围绕当前主线优先排序，支持小屏滚动。

手机书籍后来被暂停、完成、删除或更换主线，不能导致尚未上传的腕端记录丢失。

如果腕端脱机期间使用了过期书籍目录，完成记录仍要保留，导入时根据手机当前事实判断是否可以更新进度。

不通过同名书籍自动认定为同一个 ID。

### 六、第四阶段：结束后同步协议

基于已验证的 system.interconnect，新增离线同步能力协商及严格版本协议；保留现有 v1 只读和 v2 控制兼容性。

同步优先级：

1. 上传已完成且未确认的腕端记录。
2. 手机验证并在持久化事务中导入或去重。
3. 手机返回记录 ID 和校验信息对应的确认。
4. 手环收到确认后标记已同步。
5. 之后再更新本地书籍目录和页码信息。

每条腕端记录使用稳定设备安装身份 + 本地 Session ID 形成去重键。手机端必须建立数据库唯一约束，不依赖内存缓存实现去重。

采用有限批次、分片及 ACK，不超过现有可承受的无线消息预算。不用一次大 JSON 传所有历史。

手机收到部分分片、校验失败、应用退出、蓝牙中断时，不得创建不完整的学习记录。

ACK 仅代表手机已完成持久化提交，不代表网络发送成功。ACK 丢失时重新上传同一个 ID，手机应安全返回已存在状态。

手环应用不运行时的后台自动同步能力尚未得到证明。第一版保证在通信可用且腕端 Mirra 运行时自动进行，无需点击同步；后台无感同步只能在实测支持时作为增强能力。

禁止建立第三方服务器、云账户或额外 Bridge App。

### 七、第五阶段：Android 接收与统一阅读历史

在现有 Android Mirra 代码上增加腕端已完成记录的独立导入模型，而不是向现有唯一活动 Session 强行插入另一台设备的 Session。

保持原有学习算法与 Room 事务约束。

如果需要 Room Schema 迁移，提供明确的新版本迁移测试；新增记录和去重收据必须进入正式备份与恢复流程，旧备份应安全兼容，未知格式不能静默覆盖。

统一阅读历史中明确显示：

- 来源：手机／手环；
- 实际阅读区间和休息区间；
- 时长与可靠性标记；
- 第一动作确认事实；
- 可选页码；
- 腕端未监测状态。

统计层按可信 FOCUS 区间的并集处理双端时间重叠，不把整场 Session 中的休息计入学习时间。原有手机 FULL/PARTIAL/NONE 和有效专注规则保持原含义。

同书同步进度取更高的有效页码。若书籍缺失、进度超范围、数据损坏或时间不可信，保留独立原始记录，不擅自修改书籍进度。

### 八、模式边界

手环的「独立学习」与「控制手机学习」是两种独立业务所有权。

已有腕端独立 Session 时，不允许在线控制结果覆盖该 Session，不允许连接恢复后自动切换成手机 Session。

手机同时存在另一场学习，允许保留双端原始记录，统计层自行处理重叠，不强行把两场记录合并。

进入不同模式必须有明确的界面提示。旧版手机无法协商新同步能力时，手环独立记录仍然安全保存在本地，等待兼容版本。

### 九、界面设计

继续使用已批准的深墨背景与 Mirra Blue。

首页优先展示当前独立学习状态。无活动学习时优先展示主线书籍和「开始学习」。

独立学习页面需要：书籍、第一步、学习计时、休息选择、主动继续、结束保存。

完成记录只展示简洁同步状态：待同步、正在同步、已同步、需要处理。不增加复杂的设备诊断占位页面。

首版不做笔记输入、自由文字输入、复杂趋势、全天后台通知和分心识别。

界面必须适配国行 9 Pro 的真实 336 × 480 屏幕与 168 设计宽度，使用真实设备确认触控、滚动、长书名和中文截断。

### 十、开发与交付纪律

先核对两个仓库、最新 Module 04 分支与未提交工作，继承现有已通过的通信实现，不重新造轮子。

先研究相关开源 Vela 项目和许可证，优先复用可靠的轻量思路，不直接引入未经评估的大型框架。

阶段依次为：真实持久化实验 → 腕端独立闭环 → 离线目录 → 同步协议 → 手机导入及统计 → 自然使用验证。

内部普通开发任务由 Codex 自主执行，不要求用户逐项验收。

涉及真机安装、设备重启、权限、手机数据库迁移风险或原有数据不可逆变更时，必须停在明确的安全边界，取得当前授权。

不卸载原应用、不清数据、不重新签名、不降级、不修改原手机工作区、不自动合并 main。

交付时区分：

- 真机已经证明的功能；
- 自动化和模拟器证明的功能；
- 尚未执行或受系统限制的功能。

提供 APK/RPK、版本、SHA-256、证书核对、两端功能分支和简洁交付报告。

沿用用户已决定的“自主开发＋自然使用反馈”，不重复安排冗长人工验收矩阵。

本合同是待实施方案；正式代码执行与设备操作仍以用户授权为准。

## 六、开发路线建议

我建议调整原来以震动提醒为下一阶段的安排，优先做这条主线：

| 阶段  | 目标            | 是否需要真机证明     |
| --- | ------------- | ------------ |
| 05A | 手环持久化与重进恢复    | 必须           |
| 05B | 独立开始、休息、继续、结束 | 必须           |
| 05C | 主线和选定书籍离线目录   | 需要           |
| 05D | 结束后双向同步、去重    | 必须           |
| 05E | 手机统一历史、进度与统计  | 自动化为主，配合自然使用 |

最关键的是 05A。 它直接决定这款产品能不能真正做到手机不在身边时仍然可靠使用。

如果这项成立，后面的独立学习、同步协议和统一阅读历史都有了坚实基础；如果不成立，我们就应该先解决手环真实设备上的存储问题，而不是急着开发漂亮界面或增加功能。

到这里，你之前通过苏格拉底式讨论确定的产品规则，已经可以整合为一套完整的独立版 V1 设计了。

我的建议是以这份方案作为开发基线，下一步先授权 Codex 完成 05A 的非破坏性技术验证。 不应在证明手环能可靠保存独立学习状态之前，就改动你手机上的学习数据库。
